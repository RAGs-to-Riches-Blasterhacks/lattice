# Lattice Backend

Lattice is a skill-building app where an LLM agent creates personalized learning plans. This is the FastAPI backend that manages users, plans, conversations, and streaks, backed by MongoDB.

The defining feature of the plan system is **git-like branching**: when a user fundamentally changes what a learning node is about, the graph forks into a new branch and all subsequent nodes are regenerated by the LLM to reflect the new direction.

## Quick Start

```bash
# 1. Configure environment
cp .env.example .env
# Edit .env with your MongoDB Atlas connection string

# 2. Install dependencies
pip install -r requirements.txt

# 3. Run the server
uvicorn main:app --reload
```

Verify with `GET /health` — should return `{"status": "ok"}`.

## MongoDB Setup

The project uses **MongoDB Atlas** for both local development and production. There is no local MongoDB instance — all environments connect to Atlas.

| Environment | Database | Notes |
|---|---|---|
| Local dev | `lattice-test` | Dev database on your Atlas cluster, set via `.env` |
| Production | Production DB name | Atlas production cluster, configured via deploy environment variables |

Your `.env` should contain your Atlas connection string:

```
MONGO_URI=mongodb+srv://<user>:<password>@<cluster>.mongodb.net/?retryWrites=true&w=majority
MONGO_DB_NAME=lattice-test
```

The `.env` file is gitignored. Never commit Atlas credentials.

## The Plan Graph System

### How Plans Work

A plan is a directed graph of **PlanNodes**. Each node represents a learning task for a given position in the sequence (identified by `node_number`).

When a plan is first created by the LLM, it's a **linear chain**:

```
[Node 1] --> [Node 2] --> [Node 3] --> [Node 4] --> [Node 5]
                          (all on "main" branch)
```

Every plan has at least one **Branch** — the `"main"` branch, created at plan generation time. The plan's `active_branch_id` points to whichever branch the user is currently viewing (like `HEAD` in git).

### Node Options (Not Branches)

A single node can offer **options** — alternative approaches to the same learning objective. For example:

```
Node 3: "Learn Recursion"
  Option A: "Watch video series on recursion" [selected]
  Option B: "Work through recursive coding exercises"
  Option C: "Read SICP chapter on recursion"
```

All options lead to the **same next node**. Switching which option is selected is a non-core change — it doesn't alter the graph structure or trigger branching. Options are "different how, same what."

### Core Changes and Branching

The graph branches when a user makes a **core change** to a node — changing its fundamental learning objective.

**Core fields** (changing these triggers a branch):
- `title` — the node's learning objective
- `description` — the detailed task explanation
- `options[].title` or `options[].description` — what an option fundamentally is

**Non-core fields** (these edit the node in place, no branch):
- `status`, `notes`, `activity_log`, `completed_at`, `scheduled_date`
- `options[].is_selected`, `options[].resources`
- `skill_level`, `type_of_task`

### How Branching Works

When the user changes Node 3's title from "Learn Recursion" to "Learn Iteration Instead", the system:

1. **Creates a new Branch** ref pointing to the divergence point (Node 2)
2. **Creates the modified node** as a new PlanNode on the new branch
3. **Creates placeholder nodes** for all subsequent positions (4, 5, ...) with `needs_regeneration = True`
4. **Sets `active_branch_id`** to the new branch
5. **Increments `generation_version`** to signal the frontend
6. **Does NOT delete the original nodes** — they remain on the `"main"` branch

```
                              "main" branch
[Node 1] --> [Node 2] --> [Node 3: Recursion] --> [Node 4] --> [Node 5]
                  |
                  +------> [Node 3: Iteration] --> [Node 4*] --> [Node 5*]
                              "branch-2"           (needs_regeneration=True)
```

The placeholder nodes (marked with `*`) carry `needs_regeneration = True`. The LLM receives the shared prefix (Nodes 1-2) plus the changed node and regenerates content for each placeholder to create a coherent learning path.

### Resolving the Active Path

The frontend needs to know which nodes to display. `get_active_path(plan)` resolves this by:

1. Starting at the active branch
2. Collecting all nodes on that branch
3. Walking up through `parent_branch_id` to collect shared ancestor nodes (up to each `diverged_from_node_id`)
4. Returning the full sequence in `node_number` order

For a branch-of-a-branch, this walk is recursive — the shared prefix may span multiple ancestor branches.

### Switching Branches

Users can switch back to any non-archived branch. This just sets `active_branch_id` to the target branch — all nodes from all branches remain in the flat `Plan.nodes` array. No data is deleted.

### Git Concept Mapping

| Git | Lattice |
|-----|---------|
| Repository | `Plan` document |
| Commit | `PlanNode` |
| Branch ref | `Branch` (embedded, lightweight pointer) |
| HEAD | `Plan.active_branch_id` |
| Parent commit | `PlanNode.prev_node_id` / `next_node_ids` |
| Fork point | `Branch.diverged_from_node_id` |
| Commit history | `get_active_path()` traversal |

## Key Models In Detail

### PlanNode

| Field | Type | Purpose |
|---|---|---|
| `node_id` | uuid | Unique across the entire plan |
| `branch_id` | uuid | Which branch owns this node |
| `node_number` | int | Position in the sequence |
| `title` | str | Learning objective (core field) |
| `description` | str | Detailed task (core field) |
| `skill_level` | str? | `beginner` / `intermediate` / `advanced` — per node |
| `type_of_task` | str? | Classification tag (e.g. `reading`, `exercise`, `project`) |
| `options` | NodeOption[] | Alternative approaches within this node |
| `resources` | Resource[] | Links/videos/exercises (used when no options) |
| `status` | enum | `not_started` / `in_progress` / `completed` / `skipped` |
| `needs_regeneration` | bool | Flagged for LLM to regenerate after branching |
| `notes` | NodeNote[] | User's personal notes |
| `activity_log` | ActivityEntry[] | Check-in dates for streak tracking |

### SuccessLevels (on Plan)

Three tiers of expected outcomes:

| Field | Meaning |
|---|---|
| `should_know` | What the user should be able to do/know by the end |
| `might_know` | Stretch goals the user might achieve |
| `should_know_next` | What the user should tackle after this plan |

### Streak

One document per user. Global across all plans — any check-in on any node on any plan counts. Check-ins ("I worked on this today") are separate from node completion. A node can have many check-in days before being marked complete.

When a user checks in:
1. Today is appended to the node's `activity_log`
2. Today is appended to the global `Streak.activity_dates`
3. `current_streak` and `longest_streak` are recomputed by walking backward through consecutive dates

## Plan Service API

`app/services/plan_service.py` contains the core branching logic:

| Function | Purpose |
|---|---|
| `is_core_change(node, changes)` | Returns `True` if the changes alter the node's learning objective |
| `create_branch(plan, node_id, changes)` | Forks the graph at the given node, creates placeholders |
| `get_active_path(plan)` | Resolves the full visible node sequence for the active branch |
| `switch_branch(plan, branch_id)` | Points `active_branch_id` to a different branch |
| `apply_node_edit(plan, node_id, changes)` | Routes to in-place edit or branch creation; returns `(plan, did_branch)` |

## Auth

Users authenticate via **Firebase Auth**. The `User` document stores `firebase_uid` and `email` from Firebase — no passwords are stored in MongoDB. The `get_current_user` dependency (`app/core/security.py`) validates Firebase ID tokens on incoming requests and resolves the corresponding `User` document.

All auth endpoints return three tokens:

| Token | Purpose |
|---|---|
| `id_token` | Firebase ID token (JWT) — use as `Bearer` token for authenticated API requests |
| `refresh_token` | Use to obtain a new `id_token` when the current one expires |
| `custom_token` | For Flutter SDK — pass to `signInWithCustomToken()` |
